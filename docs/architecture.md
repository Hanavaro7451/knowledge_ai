# AI Knowledge Platform — архитектурные решения

**Статус:** рабочие ADR, изменения допускаются с объяснением компромиссов.

## Контекст и контур MVP
Swagger UI / HTTP-клиент → **FastAPI** (auth, documents, query) → PostgreSQL/pgvector, MinIO, Celery/Redis, Ollama. Backend — отдельный сервис, без привязки к будущему UI. Стиль — **модульный монолит**, не микросервисы.

### Логический pipeline загрузки
1. Создать Document (`UPLOADING`) в PostgreSQL, используя устойчивый UUID и предсказуемый object key.
2. Сохранить PDF в MinIO → обновить статус на `UPLOADED`.
3. Поставить задачу индексации в Celery/Redis → `PROCESSING`.
4. Worker: извлечение текста PDF (с номерами страниц) → структурный chunking → локальные embeddings.
5. Короткая транзакция БД для атомарной публикации готовых chunks и `READY`; при ошибке — контролируемый статус/повтор, без частично опубликованного индекса.
6. Упавшие/зависшие задачи и рассинхронизация БД/MinIO требуют восстановления; его конкретный механизм определить перед реализацией (не обещать надёжность без тестов).

### Логический pipeline RAG
Проверить JWT и owner → проверить `document_id` и `READY` → embedding вопроса в той же модели → Top-K поиск pgvector с ограничением документа/пользователя → передать **content** найденных фрагментов в локальную LLM → структурная проверка источников → ответ + ссылки с метаданными backend. Текст документов — недоверенный ввод (prompt injection risk).

## Принятые решения
| ID | Решение | Почему / оговорка |
|---|---|---|
| ADR-001 | Сначала запись в PostgreSQL, затем файл в MinIO | Наблюдаемость, fail-fast, контроль незавершённых загрузок; обе системы не объединены одной транзакцией |
| ADR-002 | Идемпотентность загрузки и индексации | Избегать дублей при ретраях; отдельный `Idempotency-Key` для повтора операции ≠ SHA-256 для дедупликации содержимого. Реализацию ключей ещё уточнить |
| ADR-003 | Для MVP GET/polling; SSE после MVP | Простота тестирования; ранее обсуждался SSE как целевой вариант |
| ADR-004 | Кооперативная отмена обработки при удалении — после MVP | Без жёсткого убийства процесса; нужен контроль гонок и фоновая очистка |
| ADR-005 | Валидация LLM на backend + максимум один corrective retry | Подпись источников не доверяем модели; валидные ID не доказывают фактическую корректность |
| ADR-006 | Ограничение параллельности и ожидания LLM | GPU — узкое место; 2 активных + 8 ожидающих лишь гипотеза для замеров; semaphore процесса не глобален |
| ADR-007 | Owner-only доступ | `documents.owner_id -> users.id`; фильтрация на уровне SQL, включая pgvector, не только UI |
| ADR-008 | RAG по одному выбранному документу | Меньше сценариев и проще диагностика; поиск по всем — позже |
| ADR-009 | Вопросы без истории диалогов | MVP не хранит conversations/messages; история — приоритетное расширение |
| ADR-010 | Текстовые PDF без OCR | Упрощает pipeline; сканы должны получить понятную ошибку |
| ADR-011 | Одна фиксированная embedding-модель и размерность | Нельзя смешивать векторы разных моделей; смена требует реиндексации, даже при одинаковой размерности |
| ADR-012 | Embeddings chunks вычисляются при индексации | На каждый вопрос рассчитываем только embedding запроса; кеш ответов — отдельная будущая оптимизация |
| ADR-013 | Backend-first, UI вне MVP | Swagger и HTTP-клиент сначала, позднее отдельный PySide6 клиент |
| SEC-001 | Rate limiting login | Redis-счётчики, 429, нейтральные ошибки, безопасные логи; параметры уточнить |
| SEC-002 | Fail closed для login при недоступной защите лимитов | 503 вместо входа без rate-limit; не отключать излишне другие безопасные маршруты |

## Предварительные сущности
- **User:** `id`, `username`, `email`, `password_hash`, `is_active`, `created_at`; уникальность email на уровне БД с определённой нормализацией.
- **RefreshSession:** идентификатор/хеш refresh, `user_id`, expiry, revoked/rotated metadata; детали определить при реализации.
- **Document:** `id`, `owner_id`, `filename`, `content_type`, `size_bytes`, `storage_key`, `status`, `created_at`, `updated_at`, `error_message`.
- **DocumentChunk:** `id`, `document_id`, `content`, `chunk_index`, `page_number`, `embedding` (`pgvector.Vector` с размерностью модели).
- **ProcessingTask:** опциональная таблица, не создавать без обоснования (Celery уже имеет механизм задач; нужно решить, какие состояния сохраняем в своей БД).

Связи: User 1:N Document; Document 1:N DocumentChunk. При разработке DELETE помнить: каскады PostgreSQL не удаляют объекты MinIO.

## Неопределённости до реализации
- Конкретная Ollama LLM и embedding-модель, размер вектора, chunk size/overlap и Top-K — по эксперименту.
- Выбор PDF parser, представление многополосных/многостраничных chunks и номера страниц.
- Схема refresh-ротации/хранилища сессий и политика rate-limits.
- Как обработать сетевой обрыв во время upload и повторный `Idempotency-Key` с отличающимся телом.
- Когда и как восстанавливать повреждённые/зависшие ingestion tasks и делать reconciliation с MinIO.
- Область atomic publish, защита от конкурентных повторных индексаций.

Не решать всё заранее. Вести ADR при конкретных задачах; сначала рабочий вертикальный срез, затем измерение и улучшения.
