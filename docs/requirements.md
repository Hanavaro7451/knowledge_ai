# AI Knowledge Platform — требования MVP

**Версия:** 1.0-draft (ревью основных требований завершено; технические контракты уточняются перед реализацией)  
**Статус:** согласованные границы MVP, без реализации  
**Формат:** backend-first pet/portfolio project, Python Backend + Applied AI  
**Бюджет:** 0 ₽: локальные модели и инфраструктура

## 1. Цель
Авторизованный пользователь загружает PDF с текстовым слоем, дожидается индексации, выбирает **один свой** готовый документ, задаёт независимый вопрос и получает ответ локальной LLM с проверяемыми ссылками на фрагменты и страницы исходного PDF.

## 2. Функциональные требования
### AUTH
- Регистрация: `username`, `email`, `password`; сервер задаёт `id`, `created_at`, `is_active`; пароль хранится только как Argon2id-хеш. Email уникален в БД, регистр нормализуется по согласованному правилу.
- Вход по email и паролю. Access JWT — короткоживущий (ориентир 15 минут), refresh — более долгий (ориентир 7 дней). Для refresh предусмотрены ротация и отзыв (серверное хранение хеша/идентификатора сессии).
- Доступ к собственному профилю, logout. Неверные реквизиты не раскрывают существование email; rate limiting и обработка сбоя защиты.
- У каждой записи Document есть `owner_id`. Любой доступ к документам, chunks и векторному поиску ограничивается текущим пользователем на уровне backend/SQL. Для чужого документа возвращаем 404 без раскрытия существования.

### DOC
- Принимать PDF до 100 МБ **включительно**; проверять размер, формат и возможность извлечения текста. В MVP сканы/изображения без текстового слоя отклоняются без OCR.
- При начале загрузки создавать метаданные в PostgreSQL, затем сохранять оригинал в MinIO; отслеживать статусы `UPLOADING`, `UPLOADED`, `PROCESSING`, `READY`, `FAILED`.
- Индексация выполняется фоновым воркером независимо от открытой вкладки. Извлечь текст со страницами, разбить на chunks по структуре текста, сгенерировать локальные embeddings, сохранить в pgvector.
- Индексация должна быть безопасна при повторной попытке: нельзя публиковать частично сформированный индекс или плодить дубликаты. Не держать транзакцию PostgreSQL открытой во время долгих обращений к модели.
- Список собственных документов и получение статуса через HTTP. В MVP можно использовать polling; SSE позже.
- Повторная обработка после ошибки — отдельный API-контракт, который требуется уточнить до реализации. Для загрузки обсуждался Idempotency-Key; детали жизненного цикла ещё подлежат уточнению.

### RAG
- Пользователь выбирает **один** документ владельца со статусом `READY`.
- Для вопроса генерируется embedding той же моделью, что и для chunks. Поиск Top-K с фильтрами по `document_id`, `owner_id` и состоянию документа. Храним `content`, `document_id`, `chunk_index`, `page_number`, `embedding`.
- Локальная LLM (через Ollama) получает найденные **тексты** и формирует ответ только по ним. Неизвестные ответы не додумывать, явно сообщать о недостатке данных.
- Сервер валидирует структуру ответа и разрешённые идентификаторы источников, самостоятельно формирует проверенные ссылки на документ/страницы. При исправимой ошибке — максимум одна корректирующая попытка; далее безопасная ошибка.
- Каждый вопрос независим. История диалога не хранится и не передаётся в модель.

## 3. Нефункциональные требования
- Непроверенный PDF и его текст считаются недоверенными данными: не должны менять инструкции модели или правила авторизации.
- Локальные сервисы не публикуются наружу без необходимости. Секреты — через переменные окружения/локальные секреты, `.env` с паролями не коммитить.
- Ограничивать время ожидания, длительность внешних операций, количество параллельных обращений к LLM и длину очереди; конкретные лимиты устанавливаются по замерам. Ранее обсуждалась отправная точка 2 активных + 8 ожидающих, **не гарантированное производственное значение**.
- При недоступности Redis, когда он обязателен для проверки лимитов входа, новые входы завершаются 503 (fail closed). Наличие валидного access JWT не требует автоматически отключать весь API, если нужные для запроса зависимости доступны.
- Обрабатывать ошибки зависимостей; логировать без паролей и токенов.
- Pytest unit/integration, mock LLM для тестов без Ollama. Docker Compose для локального окружения.

## 4. Предварительные API (контракты уточнить)
| Метод | Маршрут | Действие |
|---|---|---|
| POST | `/api/v1/auth/register` | Регистрация |
| POST | `/api/v1/auth/login` | Вход |
| POST | `/api/v1/auth/refresh` | Ротация токенов |
| POST | `/api/v1/auth/logout` | Отзыв refresh-сессии |
| GET | `/api/v1/users/me` | Текущий профиль |
| POST | `/api/v1/documents` | Загрузка PDF |
| GET | `/api/v1/documents` | Список своих документов |
| GET | `/api/v1/documents/{id}` | Метаданные и статус |
| POST | `/api/v1/documents/{id}/retry` | Повторная индексация (уточнить) |
| POST | `/api/v1/query` | Вопрос по одному `document_id` |
| GET | `/api/v1/health` | Healthcheck |

Ответ регистрации: 201 без `password_hash`; конфликт email: 409; невалидная авторизация: 401; недоступный/чужой документ: 404; превышение rate limit: 429; зависимость недоступна: 503.

## 5. Приёмка MVP
1. **Happy path:** регистрация/вход, загрузка текстового PDF, `READY`, вопрос, корректный ответ с проверяемым источником/страницей.
2. **Нет ответа в документе:** ассистент не изобретает данные, сообщает о недостатке сведений.
3. **Ошибки ввода:** запрос с опечатками и грамматическими ошибками по возможности приводит к верному поиску; при неоднозначности система не выдумывает.
4. **Изоляция:** пользователь B не может прочесть документ A по UUID и не получает его сведения через поиск/генерацию.
5. Невалидный/сканированный PDF и сбои индексации обрабатываются контролируемо; частичный результат не попадает в выдачу.
6. Основные unit/integration-тесты проходят; окружение запускается по README.
